# Anti Pattern Name

## 한 줄 요약

자주 발생하는 실수와 그로 인해 생기는 비용을 한 줄로 정리합니다.

## 패턴 형태

- 분류: Anti Patterns
- 형태: 문제 패턴 / 리팩터링 가이드
- 목적: 어떤 문제 징후를 발견하고 어떻게 개선할지 정리합니다.

## 왜 문제가 되는가

처음에는 편해 보이지만 시간이 지나며 변경 비용을 키우는 이유를 설명합니다.

## 핵심 원리

- 이 문제가 어떤 불가능한 상태, 중복 소스, 불안정한 참조, 누락된 생명주기 처리를 만드는지 적습니다.
- 공식 문서나 신뢰 가능한 자료에서 어떤 원칙과 충돌하는지 적습니다.
- 금지 규칙이 아니라 리팩터링 신호로 설명합니다.

## 기본 코드 형태

```tsx
// 나쁜 예: 어떤 상태 꼬임, 중복 소스, 불안정한 참조가 생기는지 최소 코드로 보여줍니다.
// 좋은 예: 같은 요구사항을 더 작은 책임 경계나 단일 출처로 표현합니다.
```

## 실무 판단 기준

- 문제가 실제 사용자 흐름에서 어떻게 재현되는지 적습니다.
- 변경 요구가 들어왔을 때 어떤 파일과 상태를 함께 수정해야 하는지 적습니다.
- 개선 후 불가능한 상태, 중복 소스, 불안정한 identity, 누락된 cleanup이 어떻게 줄어드는지 적습니다.
- 예외적으로 괜찮은 단순 케이스와 적용하지 않을 신호를 함께 적습니다.

## 예제에서 확인할 것

- 좋은 예에서 문제가 어떤 책임 경계로 이동했는지 적습니다.
- 나쁜 예에서 실제로 어떤 상태 꼬임, 중복, 누락, 변경 비용이 발생하는지 적습니다.
- 사용자가 직접 눌러 보거나 입력해 볼 수 있는 재현 단계를 적습니다.

## 예제 읽는 법

- `BadCase.tsx`에서 먼저 재현 단계를 실행합니다.
- `Example.tsx` 또는 `ImprovedCase.tsx`에서 같은 요구사항이 어떤 단일 출처, 안정 id, 분리된 책임으로 표현되는지 봅니다.
- 실제 코드 리뷰에서는 예제의 원칙을 그대로 복사하기보다 현재 팀의 데이터 fetching, form, design system 경계에 맞춰 적용합니다.
